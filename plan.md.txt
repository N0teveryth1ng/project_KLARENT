# 2. Product definition

**Working name: Agent Reliability Lab**

### What it does

Agent Reliability Lab is a web-based autonomous QA execution and evaluation platform.

A user defines a browser-based testing scenario. The system executes that scenario against a controlled demo application, observes browser behaviour, verifies expected outcomes, handles failures, and produces an execution report.

The platform should demonstrate that an autonomous QA system can do more than successfully execute a happy-path test.

It must demonstrate that the system can:

- Execute browser workflows reliably.
- Detect unexpected application behaviour.
- Identify failed execution steps.
- Recover from transient failures.
- Avoid repeating completed side effects.
- Preserve execution state across interruptions.
- Distinguish genuine failures from recoverable failures.
- Produce evidence-backed test results.
- Measure reliability across repeated executions.

### Core engineering question

Can an autonomous browser-testing system reliably complete a workflow when the browser, application or network behaves unpredictably?

Every major engineering decision should contribute to answering this question.

# 5. Autonomous QA execution engine

This is the core of the project.

Build a step-based execution engine.

A scenario consists of multiple ordered steps.

Each step should contain:

- Unique step ID.
- Action type.
- Target element or locator.
- Input data, if required.
- Expected outcome.
- Timeout.
- Retry policy.
- Verification conditions.

Example:

    Scenario: Purchase a product

    Step 1: Open application
    Step 2: Log in
    Step 3: Search for product
    Step 4: Open product page
    Step 5: Add product to cart
    Step 6: Open checkout
    Step 7: Submit order
    Step 8: Verify order creation

Implement reusable action types:

- Navigate.
- Click.
- Fill.
- Select.
- Wait.
- Assert visible.
- Assert text.
- Assert URL.
- Screenshot.
- Verify application state.

The engine must not blindly assume an action succeeded because Playwright returned without throwing an exception.

Every important action must have an explicit postcondition or verification strategy.

Persist execution results after each step.

### Execution states

Use explicit states:

- PENDING
- RUNNING
- PASSED
- FAILED
- RETRYING
- RECOVERED
- CANCELLED
- INTERRUPTED

Define valid state transitions.

Do not allow arbitrary state changes.

# 6. Failure injection and resilience testing

This is one of the most important parts.

Create a controlled failure-injection framework.

The system should support deliberate failures during execution.

### Failure types

**A. Browser failures**
- Browser process termination.
- Page crash.
- Navigation timeout.
- Element not found.
- Stale or changed page state.

**B. Network failures**
- Temporary request timeout.
- HTTP 500 response.
- Connection interruption.
- Slow response.
- Request failure.

**C. Application failures**
- Unexpected validation error.
- Failed API request.
- Delayed application response.
- Application state mismatch.

**D. Execution failures**
- Worker process termination.
- Execution interruption between steps.
- Restart after persisted state.
- Duplicate execution request.

Implement a failure-injection configuration per scenario.

Example:

    Scenario: Checkout recovery

    Failure injection:
        type: network_timeout
        target_step: submit_order
        occurrence: 1
        duration: 3 seconds

The framework should allow deterministic reproduction of failures.

Never inject failures randomly by default. Reproducibility matters more than unpredictability.

# 7. Retry and recovery engine

Implement controlled retry behaviour.

Retries must be based on failure classification.

### Retryable failures

Examples:
- Temporary network timeout.
- Browser navigation timeout.
- Temporary HTTP 5xx.
- Browser process interruption where recovery is possible.

### Non-retryable failures

Examples:
- Invalid user credentials.
- Failed business assertion.
- Missing required test data.
- Invalid input.
- Permanent authorization failure.

Implement:

- Configurable maximum retries.
- Exponential backoff.
- Retry limits.
- Failure classification.
- Retry history.
- Retry timestamps.
- Recovery verification.

Do not retry every exception.

A retry must not automatically repeat a side effect.

### Recovery behaviour

When a step fails:

1. Capture the error.
2. Persist its execution state.
3. Classify the failure.
4. Determine whether recovery is possible.
5. Check whether the step's side effect already occurred.
6. Retry only when safe.
7. Verify the expected postcondition.
8. Record the final result.

The system must distinguish between:

- Original execution failure.
- Retry attempt.
- Successful recovery.
- Permanent failure.

# 8. Idempotency and duplicate side-effect prevention

This is a critical engineering requirement.

Demonstrate what happens when execution is interrupted immediately after an external side effect.

Example:

The browser submits an order.

The application successfully creates the order, but the browser loses its connection before receiving confirmation.

The execution engine sees a timeout.

Blindly retrying the submit action could create another order.

Prevent this.

### Required design

Implement an action execution ledger.

Each side-effecting action should have:

- Run ID.
- Step ID.
- Idempotency key.
- Execution status.
- Attempt number.
- Side-effect reference, where available.
- Verification status.
- Timestamps.

Generate a deterministic idempotency key using the run ID and step ID.

The controlled demo application must support idempotent order creation through a server-side idempotency key.

On recovery:

1. Check the execution ledger.
2. Inspect whether the original action was completed.
3. Query the demo application's actual state.
4. Verify whether the order exists.
5. Reuse the existing result if the side effect already occurred.
6. Retry only when it is safe to do so.

Important engineering constraint:

Do not claim exactly-once execution simply because an idempotency key exists.

A browser action and an external application side effect cannot generally be made exactly-once through local database state alone.

Demonstrate the distinction between:
- At-least-once execution attempts.
- Idempotent application operations.
- Postcondition-based recovery.
- Duplicate side-effect prevention.

The demo must explicitly test the failure window where the side effect succeeds but its response is lost.

# 9. Persistent execution and crash recovery

The system must survive process interruptions.

Persist:

- Test runs.
- Scenario definitions.
- Individual step execution states.
- Retry attempts.
- Failure information.
- Idempotency records.
- Browser execution metadata.
- Evidence references.
- Final evaluation results.

### Recovery requirements

Simulate:

1. Start a workflow.
2. Complete several steps.
3. Terminate the execution worker.
4. Restart the worker.
5. Resume the workflow.
6. Verify previously completed steps are not blindly repeated.
7. Verify the final result.

Implement safe worker recovery.

Use database-backed execution state as the durable source of truth.

Redis may be used for coordination, locks and short-lived execution metadata, but PostgreSQL must retain the durable execution history.

Define and test behaviour when Redis becomes unavailable.

Do not make Redis availability a prerequisite for retrieving persisted execution history.

# 11. Evaluation and reliability metrics

Build an evaluation engine that calculates meaningful reliability metrics.

Required metrics:

**1. Task success rate**

Percentage of completed test runs that satisfy their expected outcomes.

**2. Recovery rate**

Percentage of eligible failed executions that successfully recover.

**3. Retry success rate**

Percentage of retry attempts that result in verified successful execution.

**4. Duplicate side-effect count**

Number of duplicate external actions detected.

**5. Mean execution duration**

Average time taken to complete a scenario.

**6. Failure distribution**

Breakdown of failures by category.

**7. Flaky test rate**

Percentage of scenarios that produce inconsistent outcomes across repeated executions.

**8. Assertion accuracy**

Track whether the final system outcome matches independently verified application state.

Do not fabricate metrics.

Run actual repeated experiments.

Make the sample size visible in the dashboard.

A 100% success rate across five executions should not be presented as evidence of production-grade reliability.

# 15. Testing requirements

Testing is a major deliverable, not an afterthought.

Use Pytest.

Implement unit tests, integration tests and end-to-end tests.

### Essential test cases

**Execution**
- Normal workflow succeeds.
- Invalid scenario is rejected.
- Failed assertion marks the run correctly.
- Completed steps are persisted.

**Retries**
- Transient failure triggers retry.
- Permanent failure does not trigger retry.
- Maximum retry limit is respected.
- Backoff is applied correctly.

**Idempotency**
- Repeated execution request does not create duplicate runs.
- Repeated action request does not create duplicate orders.
- Successful side effect followed by lost response is recovered correctly.
- Concurrent duplicate requests are handled safely.

**Crash recovery**
- Worker terminates after a completed step.
- Worker restarts and resumes.
- Previously completed side effects are not blindly repeated.
- Interrupted execution can be inspected.

**Infrastructure**
- Redis outage.
- PostgreSQL transaction rollback.
- Browser process termination.
- Worker restart.

**Evaluation**
- Metrics are calculated from actual records.
- Failed runs are counted correctly.
- Recovery metrics use the correct denominator.
- Repeated executions produce meaningful reliability measurements.

### Critical acceptance test

The following must work:

1. Start a purchase workflow.
2. Successfully create an order in the demo application.
3. Simulate losing the browser response after the order is created.
4. Interrupt execution.
5. Restart the execution worker.
6. Resume the workflow.
7. Verify the existing order.
8. Complete the run without creating another order.

The database must show one order, one verified side effect and a correctly recorded recovery.

This is the project's most important demonstration.
